# INTEGRATION — `GET /users/me` + global error envelope (DMI-72)

## Why this file exists

`ARCHITECTURE.md` covers a single-layer backend change. This file exists only because that
backend change edits `contracts/openapi/openapi.yaml`, and `frontend/src/types/openapi.d.ts`
(`frontend/package.json:12`, `openapi-typescript ../contracts/openapi/openapi.yaml -o
src/types/openapi.d.ts`) is a **checked-in, generated** artifact of that file (ADR-008) — so a
contract edit that is not followed by a regeneration produces a PR where the source of truth and
the generated type both exist in the repo but disagree, which is exactly the drift ADR-008 keeps
the file versioned to catch in review.

## Determination: regenerate as part of this feature

**Regenerate `openapi.d.ts` here, not in a follow-up.** Two reasons:

1. **Precedent.** `specs/017-auth-middleware-invite-flow/ARCHITECTURE.md` (DMI-61) made the same
   call for its own contract edits ("`frontend/src/types/openapi.d.ts` was regenerated via `npm
   run gen:types`") and treated it as part of that feature's own scope, not a deferred issue. This
   feature's contract edits are the same shape (new path, new schema, response content addition).
   **DMI-81** ("Frontend vertical slice: login → Home with live data") exists in Linear and is
   blocked by this issue, but it owns *consuming* these types, not regenerating them — deferring
   regeneration to it would leave `openapi.yaml` and `openapi.d.ts` disagreeing in the repo for as
   long as DMI-81 sits unstarted.
2. **The alternative is worse than the work.** Regeneration is one command
   (`npm run gen:types` from `frontend/`) with no manual editing — deferring it does not save
   effort, it only adds a review-time inconsistency between `openapi.yaml` and `openapi.d.ts` that
   a reviewer or CI diff would have to notice and question anyway.

## What ships as part of this feature

- `contracts/openapi/openapi.yaml` edits (see `ARCHITECTURE.md`'s "openapi.yaml additions"):
  new `users` tag, `GET /api/v1/users/me` (no `OPTIONS` twin — GET house style), new `UserProfileResponse`
  schema, the new `PasswordChangeRejected` response component (change-password's `400` repointed
  at it), `FrontendBearerAuth.description` addition, and the `content` schema added to
  `/api/v1/invites/{token}/accept`'s `410` response.
- `frontend/src/types/openapi.d.ts` regenerated by running `npm run gen:types` from `frontend/`
  after the `openapi.yaml` edits land, and committed in the same PR.

## What does not ship as part of this feature

- **No frontend runtime code.** No SPA component reads `UserProfileResponse`, no error-handling
  code branches on `error.code` yet, no role-gated UI is built. TRUTH is explicit this feature
  "unblocks all role-gated frontend UI" — it does not build it. Consuming the new type and the
  new envelope shape is separate frontend work, not part of DMI-72.
- **No change to how the frontend currently parses errors.** Verified: a grep of `frontend/src/`
  for `detail` and `error.code` returns hits only inside the generated `src/types/openapi.d.ts`
  (schema definitions and prose descriptions) — **no hand-written SPA code reads either shape
  today**. Nothing in `backend/tests/` asserts on `detail` either. So changing the error body
  shape regresses no existing consumer on either side of the boundary; this is what makes an
  app-wide envelope change safe to land in one PR.

## Verification

- After editing `openapi.yaml`, run `cd frontend && npm run gen:types` and confirm
  `git diff frontend/src/types/openapi.d.ts` shows exactly the new `users` path,
  `UserProfileResponse` type, the `PasswordChangeRejected` union on change-password's `400`, and
  the `410` response's new `content` type — no unrelated diff. An
  unrelated diff would mean the contract edit touched something beyond what `ARCHITECTURE.md`
  specifies, and should be treated as a signal to re-check the `openapi.yaml` edit, not committed
  as-is.
- No frontend test suite needs to run for this feature — there is no frontend behavior to
  exercise yet. `backend/`'s `uv run pytest` / `uv run ruff check` (per `ARCHITECTURE.md`) are the
  only required gates.

## `HUMAN_INFRA_REQUIRED`

None. `npm run gen:types` is an existing script against an existing dependency
(`openapi-typescript`, already in `frontend/package.json`); no new tooling, service, or
credential is needed.
